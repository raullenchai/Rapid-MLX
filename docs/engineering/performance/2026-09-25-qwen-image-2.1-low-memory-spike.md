# Qwen Image 2.1 8/16 GB feasibility spike (2026-09-25)

## Question

Can Rapid-MLX run Qwen Image 2.1 on 8 GB and 16 GB Macs by packaging native
MLX q4 weights for both the denoiser and the Qwen3-VL text encoder?

The existing mflux 0.20.0 path quantizes the denoiser but deliberately keeps
the text encoder in bf16. This probe temporarily removes that guard. It does
not change the supported runtime.

## Setup

- Host: Mac Studio (`Mac15,14`), 256 GB unified memory, macOS 26.5.2.
- Runtime: Python 3.11.16, mflux 0.20.0, MLX 0.32.2.
- Source checkpoint: `Qwen/Qwen-Image-2.1` revision
  `790c92633540aa0cb11d9abf19eb46d861714758`.
- Quantization: MLX affine q4 for the transformer and text encoder. The VAE
  remains unquantized.
- Memory policy: zero MLX cache, tiled VAE decode, prompt embeddings evaluated
  before encoder eviction, transformer evicted before VAE materialization.
- Probe: `scripts/probe_qwen_image_21_low_memory.py`.

The `--memory-limit-gib 8` runs set both MLX's memory and wired limits to
8 GiB. This is useful pressure, but it is not a substitute for dogfood on a
physical 8 GB Mac because macOS and other processes share unified memory.

## Results

| Checkpoint and path | Resolution / steps | Peak MLX memory | Result |
| --- | ---: | ---: | --- |
| Official bf16 encoder + on-load q4 transformer, fully materialized | 512 / 1 | 19.36 GiB | Completes; cannot fit 16 GB |
| On-load q4 encoder + q4 transformer, fully materialized | 512 / 1 | 9.22 GiB | Completes; suitable for 16 GB |
| On-load full q4, lazy execution | 512 / 1 | 13.41 GiB | Completes; bf16-to-q4 graph makes it unsuitable for 8 GB |
| Prequantized full-q4 mflux checkpoint | 512 / 40 | 4.68 GiB | Completes under the 8 GiB MLX limits |
| Prequantized full-q4 mflux checkpoint | 1024 / 4 | 5.14 GiB | Completes under the 8 GiB MLX limits |

The packaged checkpoint is 8.9 GB on disk. With the prequantized checkpoint,
the 512-square prompt-encoding phase peaked at 3.99 GiB, denoising peaked at
4.68 GiB with 3.73 GiB resident, and VAE decode left 0.94 GiB resident. The
512-square 40-step run took 52.58 seconds on this host. The 1024-square
four-step pressure run took 24.70 seconds.

The prequantized 512-square 40-step output was byte-for-byte identical to the
output produced by the same full-q4 weights before saving: no conversion drift
was introduced by the mflux save/reload path.

Two fixed-seed visual comparisons were made against the q4-transformer/bf16-
encoder path. Both full-q4 outputs preserved the requested objects, colors,
layout, and setting. In the harder prompt, both encoders rendered the exact
text `RAPID MLX` and placed a red bicycle on the left and a blue teapot on the
right. This is positive smoke evidence only; two prompts do not establish
quality parity.

## Conclusion and required implementation

The 16 GB target is feasible with comfortable headroom. The 8 GB target is
also technically feasible for 512-square generation and has promising
1024-square memory evidence, provided users download a prequantized checkpoint.
Quantizing the official bf16 checkpoint at first use cannot meet the 8 GB
target.

A production path still needs:

1. A reviewed, pinned full-q4 checkpoint containing the transformer and
   Qwen3-VL encoder in mflux layout.
2. Loader support for a quantized Qwen3-VL encoder instead of the current
   `skip_quantization=True` contract and Rapid-MLX rejection guard.
3. Explicit prompt-embedding evaluation before `MemorySaver` evicts the
   encoder. Without it, MLX's lazy graph retains encoder weights into denoise.
4. Low-memory defaults: zero or small allocator cache, tiled VAE, single-image
   batch, and component eviction between prompt, denoise, and decode.
5. A prompt suite covering text rendering, counting, spatial relations, long
   prompts, and img2img, followed by physical 8 GB and 16 GB Mac dogfood.

No 8 GB support claim should ship until that physical-machine qualification
passes. The measured MLX peak leaves roughly 2.9 GiB for macOS and non-MLX
process memory at 512 square and roughly 2.4 GiB at 1024 square.
