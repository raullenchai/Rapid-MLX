## Contrastive selection and allocation

For raw REAP sums `R[d,h,l,e]` and equal tokens per slice/half:

```
H[d,h,l,e] = R[d,h,l,e] / max(mean_e R[d,h,l,e], 1e-30)
hot[l,e] = max_{hot d, both h} H[d,h,l,e]
ratio[d,h,l,e] = R[cold d,h,l,e] / max(R[reference(language(d)),h,l,e],1e-30)
stable_cold[d,l,e] = min_h ratio >= 4
                     AND cold routed count >= 2 in EACH half
                     AND (max_h ratio - min_h ratio) / max_h ratio <= .5
candidate[l,e] = any_d stable_cold AND hot < .25 AND observed_in_any_slice
protected = hot >= .25 OR never_routed_in_any_slice
K[l] = sum_e candidate[l,e]
```

Both halves must identify the **same cold topic**; maxima from different topics
cannot fabricate stability. Language-matched reference slices prevent Chinese
versus English activation differences from masquerading as cold specificity.
General syntax/punctuation experts have ratios near one. Layer normalization
is used only for protection, not for the cross-layer distortion objective:
`D_keep(l,b) = sum_{kept e} raw_hot_REAP_max(l,e) * q(l,e,b)`.

T256 caps pruning at floor(384*.10)=38 per layer and permits only contrastive
removals. T128 caps it at floor(384*.60)=230 and permits RD fallback. All
options hard-keep hot/never-routed experts and at least routing top-6. For each
layer/precision tuple, prune contrastive experts first; then, if allowed, rank
other unprotected experts by incremental removal distortion `s_e*(1-q_e)`.
This is not lowest absolute REAP pruning. Each projection has one width for
all kept experts. Projection mode uses the sum of independently measured
projection output distortions, an additive surrogate subject to held-out checks.

The allocator enumerates admissible layer keep-count/precision options, uses
Lagrangian bisection and feasible marginal upgrades, and reports a dual bound
and gap for **this option family**. No claim of an unrestricted global optimum.
Equal three-projection parameter counts are specific to this checkpoint; exact
planned bytes are checked against the source headers before emitting an
allocation. A target that cannot satisfy protection/caps fails, without silently
relaxing them. A later owner decision would be needed to change those guards.

## Sharing, disk needs and failure behavior

Engram files are emitted under a shared source-header/config identity, then
**hard-linked** into each build with local index filenames. This preserves the
loader's existing path-containment checks and uses one physical payload. Builds
and shared directory must share a filesystem; the builder rejects cross-device
placement. Ordinary copies to another volume/repository lose deduplication;
retain shared hard links locally or explicitly account for duplicate tables.
Treat all linked payloads as immutable. Existing shared files are checked by
header and size, not a fresh 123 GB content hash. The source revision must be
immutable; modified source bytes under unchanged headers are not detected.

Streaming reserves each final header and appends tensors directly to a
`.partial` file, then atomically renames it. It does not make a second complete
shard. One source expert projection or a 65,536-row Engram chunk is read at a
time; the largest ordinary read is the ~1.324 GB BF16 embed/head matrix.
Suffixes are quantized separately to bound live memory, trading repeated CPU
work/source I/O for lower peak RAM. There is no full-job resume; a failed output
is left for inspection and must be handled explicitly before a fresh build.
Complete shared Engram files can be reused. No automatic cleanup/deletion.
