# Qwen3.5-9B engine comparison on M2 Pro

Measured 2026-08-21 on a Mac mini (Apple M2 Pro, 10 CPU cores, 32 GB unified
memory) running macOS 26.5.2. This record establishes the current Rapid-MLX
single-stream decode result for `mlx-community/Qwen3.5-9B-4bit` on that host:

> **37.42 generated tokens/s median; 37.43 tokens/s pooled.**

Use **37.4 tokens/s** when publishing a rounded result. This is decode-only
throughput for short prompts, not end-to-end throughput, prefill throughput,
TTFT, long-context performance, or concurrent serving throughput.

## Comparable autoregressive results

| Engine | Engine version | MLX version | Median tok/s | Pooled tok/s | Range tok/s | Rapid delta |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Rapid-MLX | 0.12.18 | 0.31.2 | **37.42** | **37.43** | 37.32–38.35 | — |
| mlx-vlm | 0.6.15 | 0.32.1 | 37.08 | 37.08 | 36.86–37.83 | +0.9% |
| oMLX | 0.6.3rc2 (`2df39bf`) | 0.32.0 | 36.11 | 36.02 | 33.22–36.19 | +3.6% |

All three rows use the same affine 4-bit, group-size-64 base checkpoint and
plain autoregressive decoding. The practical conclusion is parity with a small
Rapid-MLX lead on this workload; the 1–4% differences are not evidence of a
broad advantage across other Macs or workloads.

The Rapid-MLX result was repeated in a separate sustained run at 37.41 tok/s
median and 37.42 tok/s pooled (range 37.33–38.07), supporting the rounded
37.4 tok/s claim.

## Workload

- Batch/concurrency: 1
- Eight prompts: coding, explanation, JSON, reflection, dialogue, summary,
  reasoning, and translation
- Prompt length observed by oMLX: 35–78 tokens
- Maximum generation: 128 tokens per prompt; seven prompts hit 128 tokens and
  the translation prompt stopped early
- Sampling: temperature 0, deterministic seed 0, thinking disabled
- Warmup: one four-token generation before measured prompts
- Cache handling: MLX cache cleared between Rapid-MLX and mlx-vlm prompts;
  oMLX cache storage disabled
- Statistic: median of per-prompt decode throughput; pooled throughput is total
  generated tokens divided by total decode time
- Thermal state after the run: macOS reported no thermal or performance warning

The host was not proven idle with a recorded pre-run gate. Repeated results were
stable, but this remains a local engineering measurement rather than a
release-grade cross-host benchmark. Re-run on an idle host before claiming
TTFT, prefill, memory, concurrency, or statistically significant superiority.

## Reproduction

The benchmark workspace on the Mac mini was `~/qwen9-perf`. Its isolated
environments contained the versions in the table. The relevant commands were:

```bash
cd ~/qwen9-perf

venvs/rapid/bin/python bench_rapid_reuse.py \
  --model mlx-community/Qwen3.5-9B-4bit \
  --sidecar mlx-community/Qwen3.5-9B-MTP-4bit \
  --max-tokens 128 --ar-only \
  --output results/rapid-ar-only-mini.json

venvs/mlx-vlm/bin/python bench_mlx_vlm_reuse.py \
  --model mlx-community/Qwen3.5-9B-4bit \
  --sidecar mlx-community/Qwen3.5-9B-MTP-4bit \
  --max-tokens 128 --ar-only \
  --output results/mlx-vlm-ar-mini-repeat.json

venvs/omlx/bin/python bench_omlx_engine.py \
  --model mlx-community/Qwen3.5-9B-4bit \
  --condition ar --max-tokens 128 \
  --output results/omlx-ar-mini-repeat.json
```

## MTP and “MLXFast” note

Rapid-MLX's best adaptive MTP configuration reached about 34.0 tok/s median,
below its 37.4 tok/s autoregressive baseline, so MTP is not the best-performance
configuration for this model on the M2 Pro.

The available MTPLX/“MLXFast” experiment used
`Youssofal/Qwen3.5-9B-MTPLX-Optimized-Speed`, a different checkpoint, and
produced a 24.69 tok/s autoregressive median. It is excluded from the comparable
table because MLXFast is not a general engine loading the same base checkpoint;
the number must not be presented as an apples-to-apples engine comparison.
