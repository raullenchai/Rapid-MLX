# Qwen Image 2.1 source-environment dogfood (2026-09-21)

## Scope and setup

Issue [#3642](https://github.com/raullenchai/Rapid-MLX/issues/3642) requested a
distinct Qwen Image 2.1 family in the image lane, Server API, and Mac app. PRs
[#3649](https://github.com/raullenchai/Rapid-MLX/pull/3649) and
[#3652](https://github.com/raullenchai/Rapid-MLX/pull/3652) added routing and
the runtime/catalog integration. Real-weight testing found that the standard HF
cache can contain a snapshot link to a repository blob that links again into
the hub's shared blob pool. Before
[#3659](https://github.com/raullenchai/Rapid-MLX/pull/3659), the completeness
gate rejected this valid two-link chain and reported every weight missing.
With that fix, `mflux_missing_weights("Qwen/Qwen-Image-2.1")` returned `[]`
against the downloaded snapshot.

- Tested source SHA: `e46859f6c785a13877ca0ad8d66f165691f239a6` from PR #3659.
- Host: Mac mini, M2 Pro, 32 GB unified memory, macOS 26.5.2. An unrelated
  Bonsai service remained running throughout; this was not an isolated memory
  qualification.
- Runtime: Rapid-MLX 0.14.3 editable source, Python 3.11, mflux 0.20.0,
  MLX 0.32.2. The environment lived in an isolated scratch worktree and venv.
- Alias: `qwen-image-2.1` -> `Qwen/Qwen-Image-2.1` at pinned revision
  `790c92633540aa0cb11d9abf19eb46d861714758`, q8 quantization on load.
  The cataloged payload is 33,131,596,301 bytes.
- Weights were stored in the machine's shared Hugging Face cache. No second
  checkpoint or alternate cache was created.

## Reproduction and observations

Install `.[image]` from the candidate worktree into an isolated Python 3.11
environment, download the alias's pinned revision, verify
`mflux_missing_weights("Qwen/Qwen-Image-2.1") == []`, then run:

```bash
rapid-mlx serve qwen-image-2.1 --host 127.0.0.1 --port 18787
curl --fail-with-body http://127.0.0.1:18787/health
curl --fail-with-body --max-time 1800 \
  http://127.0.0.1:18787/v1/images/generations \
  -H 'Content-Type: application/json' \
  -d '{"model":"qwen-image-2.1","prompt":"A red vintage bicycle leaning against a white wall in morning light","size":"1024x1024","steps":40,"seed":42,"response_format":"b64_json"}'
```

The health route reported `ready=true`, `engine_type=image`, and
`model_name=Qwen/Qwen-Image-2.1`. The 1024-square, 40-step Server request
returned HTTP 200 and one decodable RGB PNG. Server generation took 890.00 s,
including 879.92 s of denoising. The resulting 1024-square image was a red
vintage bicycle against a white wall in morning light, matching the main
subject, color, and setting in the prompt.

Direct-engine probes on the same machine produced a valid 512-square PNG with
four steps in 48.81 s, a 512-square/40-step blue ceramic teapot image in
224.79 s, and a 512-square img2img result from that teapot in 140.58 s. The
img2img path requested 40 steps and used 24 denoising steps after applying the
runtime's strength setting. It preserved the source composition but did not
turn the blue teapot red when prompted to do so. This path is img2img
conditioning; it has not established instruction-edit fidelity.

The same Server accepted `/v1/images/edits` with the 512-square teapot as a
multipart source, the `qwen-image-2.1` alias, and `steps` omitted. It returned
HTTP 200 with one valid, 1,232,838-byte RGB PNG. The output was 1024-square:
for this family the Server derives an approximately 1024-square canvas from the
source aspect ratio. The 24 denoising steps took about 8m 49s. The result kept
the teapot and table but did not visibly follow a watercolor-style prompt,
reinforcing that this endpoint is img2img rather than instruction editing.

The four-step probe peaked at 4.74 GiB process RSS, which is not a measurement
of total unified memory. The host reported substantial pre-existing swap use,
so this run cannot establish a clean 32 GB memory floor. The unrelated Bonsai
service stayed online. The downloaded weights left about 24 GiB of disk space.

## Remaining release checks

This is evidence from an editable source environment, not an exact release
wheel or Desktop sidecar. It does not satisfy the
[release dogfood contract](../operations/image-release-dogfood-matrix.md): an
isolated cold start, a default generation request with `steps` omitted, warm repetition,
offline restart, cancellation recovery, total memory peak, and a real Desktop
journey remain unverified. A release candidate must repeat those checks against
its exact built artifact before claiming the matrix row passes.
